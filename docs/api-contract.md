# Bloom Health API Contract v1

Single source of truth for `bloom-health-service` (Go) and `bloom-health-app` (Expo/TS).
Base URL: `EXPO_PUBLIC_API_BASE_URL` (no trailing slash). All paths prefixed `/v1`. JSON only, `camelCase`, UTF-8.
Timestamps: RFC3339 UTC strings (`2026-10-17T05:00:00Z`). Dates: `localDate` = `YYYY-MM-DD` in the user's timezone. Times of day: `HH:mm` (24h).
IDs: opaque strings (UUID v4 generated by whoever creates the entity; clients create IDs for offline writes).

## Conventions
- Auth: `Authorization: Bearer <accessToken>` on everything except `/auth/*` and `/health`.
- Errors: HTTP status + `{"error":{"code":"<snake_code>","message":"<human>","details":{...}?}}`.
  Codes: `validation_failed` 400, `unauthorized` 401, `token_expired` 401, `forbidden` 403, `account_pending_deletion` 403 (`details.deleteAfter`), `not_found` 404, `conflict` 409, `rate_limited` 429 (`Retry-After` header), `internal` 500.
- Unknown JSON fields are rejected with 400. Server ignores/forbids client-supplied `role`, `userId`, `sharedSpaceId`, `createdBy`, `updatedBy`; they are derived from the token + membership.
- Every entity has `id, version (int, starts 1, +1 per accepted write), createdAt, updatedAt, deletedAt (null|ts)`. Deletes are soft (tombstones).
- Roles: `owner` may write; `viewer` is read-only. Enforced server-side per request.

## Auth
| Method/Path | Body | Response |
|---|---|---|
| `POST /auth/signup/request` | `{name, phone, email, avatar?, gender?}` | `202 {"status":"sent","challengeId"}`. Emails a 6-digit code to `email` (10 min TTL, 5 attempts, rate limited). `409 already_registered` if the email or phone is taken; `400 validation_failed` for bad input (including an `avatar` or `gender` outside the allowlist). No account exists until the code is verified. |
| `POST /auth/signin/request` | `{identifier}` (email **or** phone) | `202 {"status":"sent","challengeId"}` **always** (no enumeration): the code is emailed to the email mapped to the account; for an unknown identifier nothing is sent and the returned challengeId can never verify. |
| `POST /auth/otp/verify` | `{challengeId, code}` | `200 {accessToken, refreshToken, expiresIn (seconds, 900), user}`. For a sign-up challenge the server first creates the user (name, phone, email, and the optional signup `avatar` and `gender`), a private space (user is `owner`) and the default habits/settings. `401 unauthorized` for a wrong, expired, used or unknown challenge. |
| `POST /auth/refresh` | `{refreshToken}` | same shape as verify (refresh token rotates; reuse of an old token revokes the whole session family) |
| `POST /auth/logout` | `{refreshToken}` | `204` |

`user`: `{id, email, phone (E.164 string|null; null only for legacy accounts), displayName, avatar (string|null), timezone (IANA), theme ("forestTrail"|"midnightNavy"|"cottonCandy"|"lavenderDream"|"sunsetEmber"|"graphiteGrey"|"mintPeach"), role ("owner"|"viewer"), sharedSpaceId, ownerDisplayName, ownerAvatar (string|null), gender ("female"|"male"|"other"|"prefer_not_to_say"|null), periodTrackerEnabled (bool), deletionScheduledAt (RFC3339|null)}`. `deletionScheduledAt` is set while the account is scheduled for deletion (see `DELETE /me`). `ownerAvatar` is the avatar of the owner of the user's space (equal to `avatar` for an owner; lets a viewer show the owner's avatar). `periodTrackerEnabled` is computed: the user's explicit setting if one was made, else `gender == "female"`. It is the caller's own value (a viewer never learns the owner's). Field order is stable.

Avatars: `avatar` is `null` (no avatar; all legacy users) or exactly one of `bubu-01`, `bubu-02`, ..., `bubu-15` (case-sensitive, no whitespace). Anything else is `400 validation_failed`. On `POST /auth/signup/request` `avatar` is optional (absent or `null` = none) and is applied when the code is verified; the request is otherwise unchanged and unknown fields are still rejected.

Gender: `gender` is `null` (not provided; all legacy users) or exactly one of `female`, `male`, `other`, `prefer_not_to_say` (case-sensitive). Anything else is `400 validation_failed`. On `POST /auth/signup/request` it is optional (absent or `null` = none) and applied when the code is verified. It only drives the period-tracker default; it is never shown to other users.

Input rules: `name` 1-40 chars (trimmed) becomes `displayName`; `email` valid address <= 254 chars; `phone` is normalized to E.164 (`+<country><number>`, 8-15 digits; a bare 10-digit number gets the service default country code, `+91`) and must be unique; in `signin/request` an `identifier` containing `@` is an email, otherwise a phone. There are no passwords: every login is an emailed code. `POST /auth/otp/request` no longer exists. `PATCH /me` may also update `phone` (unique-checked; `409 already_registered` if taken).

## Profile & settings
- `GET /me` → `user`. `PATCH /me` `{displayName?, avatar?, timezone?, theme?, gender?, periodTrackerEnabled?}` → `user` (`avatar`: `null` or an allowed id, see Avatars above; `gender`: `null` or an allowed value; `periodTrackerEnabled`: `true`/`false` to set it explicitly, `null` to reset to the gender default; anything else is `400`). (Allowed for both roles; affects only own profile.)
- `POST /me/phone/request` `{phone}` → `202 {status:"sent", challengeId}`. Both roles. Emails a 6-digit code to the caller's own email; nothing is saved yet. `400` for an invalid number or your current number; `409 already_registered` if another account has it; `429` during the resend cooldown or over the limit.
- `DELETE /me` → `202 {"deleteAfter":"<RFC3339>"}`. Both roles. Schedules the caller's account for deletion 15 days later, signs out every device (refresh tokens revoked) and emails the date. Calling it again returns the same date. Until then the account is **locked**: every authenticated route except `GET /me`, `DELETE /me` and `POST /me/restore` answers `403 account_pending_deletion` with `details.deleteAfter`, and so does every route for a viewer of an owner whose deletion is pending. Signing in still works. After `deleteAfter` the account is erased permanently: profile, chats, sign-in sessions and pending codes, and for an owner the whole space (habits, logs, workouts, settings, periods, sync history) and every viewer's access to it. The email and phone can then be used for a new sign-up. An overdue account is erased at its next sign-in attempt even if the daily purge hasn't run, and the sign-in answers like an unknown account.
- `POST /me/restore` → `user` with `deletionScheduledAt: null`. Both roles. Cancels a scheduled deletion before `deleteAfter` and emails a confirmation. `409 conflict` if nothing is scheduled.
- `POST /me/phone/verify` `{challengeId, code}` → `user` with the phone saved. Both roles. A wrong, expired or another user's code is `400` (not `401`, because the caller is signed in); `409 already_registered` if another account took the number first. `PATCH /me` does not accept `phone`.
- `GET /settings` → `Settings` (shared space settings, readable by both). `PATCH /settings` (owner) `{dailyThreshold?, restDays?, restDayMode?, reminders?, stepGoal?, sundayRest?, version}` → `Settings`.
  `Settings`: `{id, dailyThreshold (0-100, default 80), restDays (int[] 0=Sun..6=Sat, default []), restDayMode ("neutral"|"counts"), sundayRest (bool, default true; absent on legacy records = true), stepGoal, reminders: Reminder[], version, updatedAt}`
  `Reminder`: `{key ("wakeUp"|"hydration"|"workout"|"eveningCheckIn"|"bedtime"), enabled (bool), time ("HH:mm")}`. Defaults: wakeUp 05:00, hydration 11:00, workout 17:00, eveningCheckIn 21:30, bedtime 21:30 (wind-down).

**Neutral days (streaks).** A neutral day never breaks the streak and does not extend it, unless enough habits are logged that day to be a normal success (with `restDayMode:"counts"` a neutral day counts as a success). Neutral days are: the effective rest weekdays (`restDays` plus Sunday (0) when `sundayRest` is true or absent) and, only while the owner's `periodTrackerEnabled` is true, every date covered by the owner's non-deleted periods (an ongoing period lasts through today).

## Period tracker (private to the owner)
`Period`: `{id, startDate (YYYY-MM-DD, not in the future), endDate (YYYY-MM-DD|null while ongoing), flow ("light"|"medium"|"heavy"; defaults to "medium" when omitted), symptoms (array, max 10, no duplicates; allowlist: cramps, headache, bloating, fatigue, mood_swings, backache, acne, nausea, cravings, tender_breasts), mood ("happy"|"calm"|"sad"|"irritable"|"anxious"|null), note (<= 500 chars|null), version, createdAt, updatedAt, deletedAt}`; sync entityType `"period"`.
Rules (violations are `400 validation_failed`, or a `rejected` sync result with reason `validation_failed: ...`): `endDate >= startDate`; at most 14 days (inclusive of both ends); the range must not overlap another non-deleted period (an ongoing period counts as lasting through today); only one period may be ongoing.
- `GET /periods?from&to` → `{items: Period[]}` (non-deleted, ascending by `startDate`; `from`/`to` optional, return periods overlapping the range). `POST /periods` → 201 Period. `PATCH /periods/{id}` (`version` required, stale → 409 with `details.server`) → Period. `DELETE /periods/{id}` → 204 (tombstone).
- **Privacy**: owner only. Viewers get `403 forbidden` on every `/periods` route and their sync push of `period` is `403`. Everything also returns `403` (push result `rejected`, reason `period_tracker_disabled`) while the owner's `periodTrackerEnabled` is false. Period rows are never returned to viewers by any endpoint: `GET /sync/pull` returns `changes.periods: []` for them (the rows are filtered out of the cursor stream), and `GET /stats/summary` exposes period days only as the generic `restDay` flag (same as Sundays), never a reason. Logs never contain period data.

## Habits
`Habit`: `{id, title, icon (string), category ("morning"|"nutrition"|"fitness"|"hydration"|"sleep"|"custom"), trackingType ("boolean"|"quantity"|"duration"|"timeOfDay"), target, targetMax (number|null), targetComparison ("atLeast"|"atMost"|"between"|"by"), unit (string|null), schedule {days: int[]}, reminder {enabled, time}|null, isActive, sortOrder, isDefault, version, createdAt, updatedAt, deletedAt}`.
- `target` for `timeOfDay` is minutes since midnight (e.g. 300 = 05:00). For `duration` minutes; `quantity` in `unit`.
- `GET /habits?includeInactive=bool` → `{items: Habit[]}`.
- `POST /habits` (owner) body: Habit minus server fields (`id` optional, client-generated allowed) → 201 Habit.
- `PATCH /habits/{id}` (owner) partial + required `version` (optimistic) → Habit; stale version → 409 `conflict` with `details.server` = current Habit.
- `DELETE /habits/{id}` (owner) soft deactivate → 204 (restore via PATCH `isActive:true`). Logs are retained.

Default habits (seeded, ids stable slugs `default-wakeup`, …): wake up by 05:00 (timeOfDay/by/300), exercise 90–120 min (duration/between/90..120), no added sugar (boolean), no junk food (boolean), dinner by 18:00 (timeOfDay/by/1080), water 2000 ml (quantity/atLeast), steps 7000–10000 (quantity/atLeast target 7000 targetMax 10000), sleep bedtime by 22:00 (timeOfDay/by/1320).

## Daily logs
`DailyLog`: `{id, habitId, localDate, value (number|bool-as-0/1|minutes-since-midnight|null), status ("complete"|"incomplete"|"skipped"|"partial"), note (string|null), source ("manual"|"device"; a write that omits it stores "manual", absent on older records = "manual"), version, updatedAt, deletedAt}`; unique per `(habitId, localDate)`. `id` = `"{habitId}:{localDate}"`.
- `GET /logs?from=YYYY-MM-DD&to=YYYY-MM-DD` → `{items: DailyLog[]}` (max 366 days).
- `PUT /logs/{habitId}/{localDate}` (owner) `{value, status, note?, source?, baseVersion (0 when creating)}` → 200 DailyLog; stale baseVersion → 409 with `details.server`. Future dates → 400.
- Status is **computed by the client/server scoring lib** from value+target when status omitted.

## Workouts
`Workout`: `{id, type ("strength"|"cardio"|"yoga"|"walking"|"badminton"|"other"), startedAt, endedAt (null while running), durationSeconds, pausedSeconds, notes, localDate, version, ...}`.
- `GET /workouts?from&to` → `{items}`; `POST /workouts` (owner, client id) → 201; `PATCH /workouts/{id}` (owner, `version` required) → Workout; `DELETE /workouts/{id}` (owner) → 204.
- Duration derived from timestamps minus `pausedSeconds`; server validates `endedAt >= startedAt`.

## Stats (server cross-check)
`GET /stats/summary?from&to` → `{currentStreak, longestStreak, days: [{localDate, completionPercent, successful (bool), restDay (bool)}], workoutCount, workoutSeconds, milestones: int[]}` computed with the same algorithm as the app's `lib/scoring`, using the owner's settings and neutral days (see above) for every caller; `restDay` is true for any neutral day and its reason is never exposed (viewers get the owner's numbers). Shared fixtures: `bloom-health-service/testdata/scoring.json` (`settings.neutralDates` lists extra neutral dates; the scoring lib itself knows nothing about Sundays or periods, the caller computes them) (copy lives in app `src/lib/__fixtures__/scoring.json`).

## Sync (offline-first)
Client keeps SQLite cache + `syncOperations` queue; direct REST writes above are also valid for online-only use; the app uses push/pull.

`POST /sync/push` (owner only; viewer → 403)
```json
{"deviceId":"uuid","operations":[
  {"operationId":"uuid","entityType":"habit|dailyLog|workout|settings|period","entityId":"...","op":"upsert|delete","baseVersion":0,"payload":{...},"clientTimestamp":"..."}
]}
```
→ `200 {"results":[{"operationId","status":"applied|duplicate|conflict|rejected","entity":{...}?,"reason":"..."?}]}`
- `applied`/`duplicate`: `entity` is the server record (authoritative); duplicate returns the originally stored result (idempotent by `operationId`, unique-indexed, retained ≥ 30 days).
- `conflict`: `baseVersion` stale. Resolution is deterministic: server record wins unless the op is a `dailyLog` upsert whose `clientTimestamp` is newer than server `updatedAt`, in which case it is applied as last-writer-wins with `version = server.version+1` and result `applied` plus `"resolved":"lww"`. Otherwise result `conflict` with `entity` = server record and the client replaces its cache and shows a "Sync issues" entry.
- `rejected`: validation/authorization failure for that op, not retryable (`reason` code).
- Max 100 operations per request; processed in order.

`GET /sync/pull?cursor=<opaque|empty>&limit=500` → `{"cursor":"<opaque>","hasMore":bool,"changes":{"habits":[],"dailyLogs":[],"workouts":[],"settings":[],"periods":[]}}`; includes tombstones (`deletedAt != null`). `periods` is only populated for the owner (always `[]` for viewers). Cursor is monotonic server sequence; client persists it only after applying a full page transactionally. Both roles may pull (scoped to their shared space).
Viewer freshness: pull on app foreground, tab focus, pull-to-refresh, and every 30 s while Home is focused. No websockets in v1.

Client retry: exponential backoff 2s→5min with jitter on network/5xx; never retry `rejected`; mark `failed` after 8 attempts (user can retry manually). Status chip: `synced | pending(n) | failed(n) | offline`.

## Chat (Bloomy, the AI assistant)
Online only: these endpoints do not go through sync. Any role may chat; every session is private to the user who created it (other users, including the owner/viewer of the same space, get `404`). v1 sends only the conversation to the model, never habits, logs, workouts, periods or profile data.
`ChatModel`: `{id, label, vendor, default (bool)}`. `ChatSession`: `{id, title, modelId, contextScopes ([], reserved), pendingMessageId (string|null: the assistant message being answered), createdAt, updatedAt}`.
`ChatMessage`: `{id, sessionId, idx (int, 0-based, ascending), role ("user"|"assistant"), content, status ("pending"|"succeeded"|"failed"), modelId, errorCode (string|null), createdAt, updatedAt}`.
- `GET /chat/models` → `{items: [ChatModel]}`.
- `POST /chat/sessions` `{title? (1-80 chars), modelId?}` → `201 ChatSession`. Default title `"New chat"`, replaced by the start of the first message. `contextScopes` other than `[]` → 400 (not supported yet).
- `GET /chat/sessions` → `{items: [ChatSession]}`, most recently updated first (at most 100). `GET /chat/sessions/{id}` → ChatSession. `DELETE /chat/sessions/{id}` → 204 (the messages are erased and the title cleared at once; later calls → 404).
- `GET /chat/sessions/{id}/messages?before&limit` → `{items: [ChatMessage] oldest first, hasMore, nextBefore (int|null)}`. `limit` 1-50 (default 30); pass `nextBefore` as `before` to load older messages.
- `POST /chat/sessions/{id}/messages` `{content (1-4000 chars, trimmed), modelId?}` → `202 {userMessage, assistantMessage}`; the assistant message is `pending` with empty `content`. Poll `GET .../messages` (about every 1.5 s) until it is `succeeded` or `failed`. One reply at a time per session: `409 conflict` with `details.reason = "turn_in_flight"` while one is pending. `429 rate_limited` (with `Retry-After`) after 100 messages per user per UTC day.

## Health
`GET /health` → `{status:"ok", time, version}` (no auth, no DB detail).

## Security notes
No DB URIs/secrets in the app. Access token 15 min (HS256/EdDSA via env key), refresh rotation, rate limits on `/auth/*` (per IP + per email). Logs never contain tokens, OTPs, wellness values, period/gender data or chat text. Chat messages are sent to a third-party model provider (Groq) by the worker; the app never talks to the provider. Period data is stored in the same MongoDB as everything else (not end-to-end encrypted); privacy is enforced by server-side filtering.
